## Intentional deviations (recorded)
1. **Search `rip:` uses the collapsed orchestrator** (as with M7 report rerip): the oracle runs a bespoke inline queue+ripper pipeline with its own status lines (`⏳ In Queue: Position #N`, `🎵 Ripping track: {id} Status: ...`); the Rust port sends the oracle's `⏳ Queuing track {id} for ripping...` status message, then the event bridge renders the standard progress lifecycle into it. On success the oracle deletes status+search messages; Rust keeps the status message (terminal completion card) and deletes only the search message — the bridge would otherwise re-send the summary as a new message if its terminal edit raced a deletion.
2. **Random `dump` + autodump pipeline runs** use `start_job` (cache-only) instead of `executeRipPipeline`'s no-msg path: a fresh `🔍 Resolving tracks from Apple Music...` message is sent first and its id passed as `status_msg_id` (same decision, M7 report rerip precedent).
3. **Autodump discovery uses direct reqwest fetches** (Catalog API playlist with scraped dev token, Marketing Tools RSS, iTunes lookup) in the bot crate — mirroring the oracle's own raw-fetch implementation rather than the engine's `PlaylistClient` (whose `PlaylistTrack` lacks release dates). The engine's `get_developer_token` (scrape + fallback + cache) is reused via the new `playlist()` accessor.
4. **Random PRNG**: `Math.random()` → xorshift seeded from clock nanos; unobservable difference (both uniform-ish picks).
5. **Scheduler first-tick semantics**: the TS `setInterval` fires after 24h; tokio's interval fires immediately, so the first tick is consumed (`interval.tick().await` before the loop) to preserve first-run-after-24h semantics.
6. **Scheduler stop-handle**: the TS `startAutoDumpScheduler` returns a cancel closure; the Rust `scheduler_loop` runs until process shutdown (no runtime stop path needed).
